# Question-First Scratch Work

Use this contract for temporary scripts, notes, prototypes, calculations, reports, fixtures, dry runs, or generated outputs created to learn something during a workflow.

## Core Rule

Scratch work answers a named question. The answer is durable only after it is captured in the appropriate repo surface or handoff evidence.

## Process

1. Name the question before creating scratch work.
2. Choose the lightest shape for that question: throwaway script, logic prototype, UI variant, calculation, fixture, data sample, dry run, note, source checklist, rendered output, or local report.
3. Keep it clearly temporary and close to the relevant context when safe.
4. Make it runnable or inspectable with one clear command or path when possible.
5. Avoid persistence, polish, broad abstractions, and production authority unless the question requires them.
6. Capture the answer in durable repo work, an accepted decision, or handoff evidence.
7. Delete, archive, fold in, or assign an owner before completion.

Scratch work is not authority by itself. Source files, docs, tests, datasets, manifests, decision records, commits, PRs, and accepted support evidence are durable authority.

## Phase Hooks

- ideation: name prototype or scratch questions before planning.
- planning: record scratch-work owner, proof surface, and disposition.
- execution: create scratch work only inside allowed side effects.
- verification: require scratch disposition before success claims.
- handoff: report deleted, archived, folded-in, or remaining scratch work with owner.
